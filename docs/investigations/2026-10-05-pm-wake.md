# Investigation: PM mail left unread, and Herdr notifications that fail

Status: three code causes for the missed wakes are shown by the code and by
new tests. The Herdr notification failures are reproduced against the
installed Herdr (0.9.1); the cause of each past failure cannot be proven from
the old logs, because they recorded no reason (see "Notification channel").

## Evidence used

Read-only copies of the live project state (`.capstan/daemon.log`,
`.capstan/state/notifications.jsonl`), and the code at the base of this branch.

- `notifications.jsonl`: herdr channel `ok:true` 60 times and `ok:false` 55
  times for `pm_message` (first failure 2026-10-02T12:06Z, last
  2026-10-05T01:17Z). Each failed line holds only `ok:false`; no reason.
- `daemon.log`: 84 `pm_woken` lines and 272 `wake_failed` lines. A sample of
  the failures is `HerdrError: agent target capstan-pm-1 not found`, retried
  every 2 s (a tick) because nothing was recorded before it failed.
  `notification_channel_failed` appears 55 times and carries only the error
  class (`HerdrError`).

## Root causes of the unread PM mail

1. **Head-only wake.** `evaluateMessaging` woke the PM only when the queue
   head (`queueHead`, the oldest non-final message) was in state `queued`. As
   soon as the PM pulled the head (`sent`) or left it `unacked`, every later
   `queued` message was invisible to the wake rule, and so was the
   operator-notification rule, which also used the head. Test:
   `a PM whose head is sent or unacked still gets a wake for a later queued
message` (test/messaging.test.ts).
2. **Wake cap.** `MAX_PM_WAKES = 5` stopped all wakes for a message after five
   lines at a flat interval (120 s), i.e. about eight minutes. A PM that was
   busy for longer was never woken again. Test: `wakes keep coming after 5`
   (intervals 120, 240, 480, 960, 1800, 1800 s), and the rewritten
   test/oversight.test.ts case.
3. **A failed prompt counted as a wake.** `recordPmWake` runs in `beforeSend`,
   before the line is typed. When the typing then failed, the ledger already
   held the wake (it counts toward the cap and restarts the interval), and the
   driver logged `wake_failed` as if nothing had happened, while a typed wake
   was logged as `pm_woken`, which read like a delivery. Nothing told the
   operator whether the PM had been reached. Test: `a wake that throws after
it was recorded is pm_wake_failed, never typed`.

There was also no signal for a PM that is reading but never acknowledges, and
nothing that said whether a wake was answered.

## Notification channel (Herdr)

`HerdrAdapter.notify` runs `herdr notification show` and throws
`HerdrError("notification_not_shown")` when Herdr answers exit 0 with
`shown:false`; any other failure of the command throws another `HerdrError`.
The notifier turned both into `ok:false` and kept only the error class in the
daemon log, so a failed line never said which.

Reproduced against the installed Herdr:

```
$ herdr notification show "Capstan test" --body "plan-18 diagnosis probe" --sound none
{"id":"cli:notification:show","result":{"reason":"no_foreground_client","shown":false,"type":"notification_show"}}
exit=0
```

Herdr accepts the command and shows nothing because no Herdr client is in the
foreground (no attached UI; notifications are tied to a foreground client).
This is the likely cause of the 55 `ok:false` lines, which sit among 60 `ok:true`
lines for the same kind of message, i.e. it depends on whether a Herdr UI is
attached when the timer fires. **UNVERIFIED for each past line**: the old logs
hold no reason, so a past failure may also have been a failed command. The
reproduction proves the mechanism, not the history.

## What the fix changes, per cause

| Cause                         | Change                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Head-only wake                | The wake target is the oldest message in state `queued`, whatever the head is. The operator notification targets the oldest pending (queued, sent, unacked) message.                                                                                                                                                                           |
| Wake cap                      | `MAX_PM_WAKES` is removed. The wait doubles from `pm_wake_interval_seconds` and is capped at `PM_WAKE_MAX_INTERVAL_SECONDS` (1800 s). Waking continues while the message stays queued and the PM is idle or done and not paused. The idle-and-empty-line guard in `wakePm` is unchanged.                                                       |
| Failed prompt counted         | A throw after the record is `pm_wake_failed` with the error; only a typed line is `pm_wake_typed`. The next wake waits for the normal backoff step. A declined wake (`pm_not_idle`, `input_not_empty`) records nothing and is retried each tick. `pm_wake_unanswered` is logged once when a wake is still unread after the next interval.      |
| Reading but not acknowledging | `[notifications] pm_stale_minutes` (default 10). One `pm_stale` notification per episode when the oldest pending message passes the threshold; the dedupe is in memory, so a daemon restart inside an episode can notify once more.                                                                                                            |
| Herdr `shown:false`           | Each `notifications.jsonl` line now carries `reason` (`not_shown`, `command_failed`, `invalid_text`, `timeout`) and a sanitized `error` (at most 200 characters). `not_shown` with `no_foreground_client` is outside Capstan: keep a Herdr client attached, or rely on the fallback channel (the status pane bell) and the stale notification. |

## Repeated wakes are by design

The wake now repeats, at most once every 30 minutes (`PM_WAKE_MAX_INTERVAL_SECONDS`),
for as long as a message stays unread. This is intended (requirement 3: wake
again until the PM pulls the message), not a leak: it replaces the old cap of
five. It never types into a busy PM or a non-empty input line: the wake only
fires when Herdr reports the PM idle or done, `wakePm` refuses with
`pm_not_idle` or `input_not_empty` otherwise, and a paused PM is not woken.
The wake stops as soon as the message leaves the `queued` state.

What the user can change: keep Herdr attached, or set
`[notifications] herdr = false` to stop the failing channel and rely on the
fallback; tune `pm_stale_minutes`.
