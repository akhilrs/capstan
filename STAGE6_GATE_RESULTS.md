# Stage 6 gate: recovery (PM-34)

Run on 2026-10-01 in a throwaway repository with an isolated Herdr session (`capstan-s6`). Every agent was the fake Claude stand-in, so no usage was spent; the default Herdr session was compared before and after and did not change. The stand-in appends the id of every instruction frame it receives to its own file, one line per delivery (`FAKE_CLAUDE_IDS_DIR`, passed to the agents with `[env] pass`); `[timers] worker_ack_timeout_seconds = 20` made the unacked step short. The evidence is in `docs/stage6-gate-evidence.txt`; tokens are not in it.

**A first attempt at this run found a production regression** that is not Stage 6's: since the Stage 5 merge the daemon passed the whole configured timers object (now holding `findingCheckSeconds`) to the message state machine, which refuses unknown keys, so every driver tick failed with `unknown timer findingCheckSeconds` and the message timers never advanced (a sent message stayed `sent` past its timeout). It was fixed and merged first as PM-38 (PR #24). This run is the second one, with the fix: the daemon log holds no `advance_failed` entry.

## What ran

1. **One worker, four instructions.** `developer-1` received instruction A (typed, acknowledged), B (typed, left unacknowledged) and C (queued behind B).
2. **`kill -9` of the daemon** with B typed and unacknowledged and C queued; the next operator command restarted it. B was not typed again and C was not delivered (the id file still held A and B once each). With the 20 s timer B became `unacked` on its own (the timers work after a restart).
3. **A recorded resend.** The operator ran `cstan resolve B retry`; B was typed once more (two lines for B) and acknowledged, then C was delivered once and acknowledged. The ledger holds one `retry` decision for B and two `sent` transitions.
4. **Work for the stale-report checks.** `developer-1` committed X1 and reported it (accepted), then committed X2 and did not report it.
5. **A killed pane.** The worker's pane was closed. Within 4.9 s the driver recorded the agent lost (three not-found observations in a row): one `agent.lost` event, one controller message to the PM that names the agent, its branch and the instruction not done, and `cstan status --watch` showed `lost: developer-1`. Instruction D, sent after the pane was gone, failed delivery (`agent_not_found`) and was never typed.
6. **`cstan replace developer-1`.** The controller released the predecessor (agent ended, its pane already gone, worktree removed) and started `developer-2` of the same role on a branch that starts at X1 (the predecessor's last accepted report), with the seed block built from the ledger: the four instructions with their states (D `failed`), the accepted report, the kept predecessor branch with its tip, and the rule that nothing failed, unacked or cancelled was done. Nothing was sent to the replacement by the controller. D stayed `failed` after the agent ended. The ledger holds `agent.replaced` for it.
7. **A new instruction E** was sent to `developer-2` and typed once.
8. **Stale reports.** The replacement reported the predecessor's unreported X2: refused (`that commit is not on your branch`); it reported X1, its own base: refused (`that commit is your base commit or older`). A second worker was replaced the same way and its old token, kept from before the replacement, was refused (`unauthorized`) on `status`, `inbox`, `report` and `ack`.

## Limits and what this run does not show

- The `kill -9` hit the daemon while B was typed and unacknowledged. A crash between recording a send and typing it cannot be hit on demand in a live run; it is covered by the failure-injection harness (`test/recovery-harness.ts`, `test/recovery.test.ts`), which stops the controller at that point and counts deliveries by the same oracle: the message ends `sent`, then `unacked`, with no delivery, and a recorded retry then delivers it once.
- The stand-ins did not do any work: the oracle counts deliveries of instruction frames, not that a real agent acts on the seed correctly. A real replacement may misread the seed block; the controller does not verify what it does with it.
- Liveness sees a gone pane or process (Herdr's `agent_not_found` or `pane_not_found`). An agent that is alive but silent is the stall timer's and the Supervisor's job. A Herdr server that restarts for longer than about twenty seconds with only one agent running would still look like a loss (a tick in which every observed agent fails together is held for ten ticks, so two or more agents are protected only for that long).
- A crash after the replacement's spawn and before `agent.replaced` is written leaves the successor active and the predecessor replaceable once more; the PM sees both in `cstan status` and releases one.
- Delivery stays at most once: a message recorded `sent` whose typing never happened ends `unacked`, visible, never duplicated.
