# Capstan MVP Plan v2

## 1. Purpose and status

**Status:** proposed with DEC-005 (PM-20). It becomes the plan of record when the PR that adds it is merged by the operator. `MVP_PLAN.md` (M0 to M3) is superseded in part: its Docker, network, egress and OMP-bridge material is history; its controller-core, ledger and recovery material is reused.

**Product:** Capstan; **CLI:** `cstan`. The operator runs `cstan` in a project. It opens the configured agent host in Herdr. The first agent is the PM: the operator types the requirement to it and talks with it. The PM asks Capstan to spawn other agents (developer, reviewer, later designer, tester and a Supervisor). Agents are interactive and persistent. The task ends when the work is integrated, independently verified and accepted.

**Evidence base.** The PM-19 spike (`docs/spike-herdr-agents.md`, experiments E1 to E6 with Claude Code in an isolated Herdr session, each run once) and an external plan review of the redesign (findings R-1 to R-9, section 14). Where this plan relies on something the spike did not test, it says so (section 12).

**Working names.** Command names (`cstan start`, `send`, `inbox`, `wait`, `ack`, `report`, `ask`, `request-review`, `finding`, `status`, `pm restart`) and the config file `capstan.toml` are working names.

## 2. Decisions taken by the operator

No Docker, no per-role networking or firewall. One trusted single-user VM. Isolation is git worktrees created by `herdr worktree create`. Containment is process-group only. Herdr stays. Agents are interactive and persistent. The PM is the interactive main agent and asks Capstan, never Herdr directly, to spawn and message agents. A separate always-on Supervisor. Claude Code first, Codex and OMP later by configuration. Per-role settings in `capstan.toml`. Build a thin vertical slice first: PM, one developer, one reviewer. The Supervisor comes after the slice. See DEC-005 for what this supersedes and for the trust model.

## 4. Architecture

```
 operator ── cstan start ──► reads capstan.toml (roles: host, model, permissions)
                              │
        ┌─────────────────────▼───────────────────────────────────────────────┐
        │ CONTROLLER DAEMON (separate process, single-instance lock)          │
        │  SQLite ledger: work, assignments, generations, messages, receipts, │
        │                 candidates, findings, events                        │
        │  Herdr adapter: the only process that sends input to, starts,       │
        │                 stops or closes agents in Herdr                     │
        │  message queue: one writer and one FIFO per recipient               │
        │  control socket (Unix, 0600): `cstan` commands from agents/operator │
        └───────┬───────────────┬───────────────┬─────────────────┬───────────┘
                │ herdr          │ herdr          │ herdr            │
                ▼                ▼                ▼                  ▼
      pane: PM (Claude Code)  pane: developer  pane: reviewer   pane: supervisor
      operator types here     worktree g1      read-only        (after the slice)
                │                │                │
                └── agents report facts by running `cstan ...` (receipts) ──┘
```

**Daemon and commands (PM-23).** `cstan start` starts the daemon (`cstan daemon` is the foreground entry point for a service manager); `cstan stop` stops it; any operator-mode `cstan` command that needs it and finds it down starts it again. There is one daemon per project: it holds the project lock, so a second start fails with the ownership error, and a foreground `cstan run` controller excludes it the same way (`cstan start` reports that owner instead of spawning). Every start runs the existing restart reconciliation, which revokes or blocks in-flight old-flow assignments and marks their runtime sessions unknown; it never creates an assignment and never touches messages, agents, waits or observations. A fresh project is created with marked placeholder inputs; the PM records the real ones as later revisions. Agents reach the daemon with `CAPSTAN_TOKEN` (that agent's current token) and `CAPSTAN_SOCKET` (the absolute socket path) in their environment; an operator-class command always uses the operator credential of the working directory's `.capstan` and never the token. The commands `inbox`, `ack`, `wait`, `send`, `resolve` and `cancel <id>` work (Stage 2e, first part; see the last block of section 5). `report`, `ask`, `request-review`, `finding`, `assign` and `pm restart` are routed and authorised and answer `not_implemented` until their stages.

Two channels:

1. **Conversation** goes through the controller's Herdr adapter: guidance, questions, answers.
2. **Facts** are `cstan` commands run inside the agent's pane: `report`, `ask`, `ack`, `inbox`, `wait`, `request-review`, `finding`. Completion is never inferred from the terminal or from Herdr's state. It is a receipt.

The controller runs with no PM alive. If the daemon dies, `cstan start` (or any `cstan` command) restarts it and reconciles. An automatic supervisor for the daemon, for example a systemd user unit, is a later item.

## 5. Messaging

`cstan send` is the only path for agent-to-agent text. The controller keeps one queue and one writer per worker pane and one strict FIFO order per recipient.

**Principle for reading panes.** Reading the screen may block or defer an action, or be shown as evidence. It never causes a state change or an automatic resend. Exactly two cases let a screen read gate an action, both logged (DEC-005): the pre-send empty-input check for worker panes, and the startup trust dialog.

**Workers (push).** A message is delivered only when the agent's Herdr state is `idle` or `done` and a read of the pane shows an empty input line. Otherwise it is `deferred`. It never sends while the agent is `working` or `blocked`. If the input line is still not empty after the maximum deferral, the controller reads and logs the text, notifies the operator, clears the line with `ctrl+u`, and then sends the message.

**The PM (pull; nothing is ever typed into the PM pane).** The operator may be typing in the PM pane, and text already in an input line merges with a later prompt (spike E4). So:

- The PM's role prompt tells it to run `cstan inbox` at the start of every turn and, only while it is actively waiting on delegated work, to call `cstan wait --timeout 90` in a loop.
- `capstan.toml` has `wait_timeout_seconds` (default 90) and `host_shell_timeout_seconds` per host, and rejects a configuration where the first is not below the second. The role prompt states the timeout. The plan reviewer reported about two minutes as Claude Code's default shell-command timeout; the spike did not test this, and Stage 2 checks it. A wait therefore ends by itself and the PM decides whether to call it again.
- `inbox` and `wait` print message text and move the message to `sent`. They do not ack. The PM acks each message with `cstan ack <id>`, as workers do. Whether the operator was notified is a separate flag (`notified_at`), not a state.
- `inbox` and `wait` also re-print the PM's own messages that are `sent` or `unacked` and not yet acked. That is a re-read, not a resend, and lets the PM ack after an interruption without the operator's help. Acking an `unacked` message moves it to `acked_late`.
- Strict FIFO applies, so `inbox` returns the oldest unresolved message and the next message becomes eligible when it is acked: one message per ack. This is a known throughput limit of the slice; batching is a later item. A gate case checks several queued worker reports (section 11, Stage 2).
- The operator's own `cstan inbox` is read-only (peek) by default, so it cannot move PM messages to `sent` unseen.
- An interrupted, timed-out or backgrounded `wait` is routine, not a residual case: the operator presses Esc to talk to the PM (the host is reported to queue typed input until the call returns, which the spike did not test and Stage 2 checks) and the model may send the command to the background. Because the ack is explicit, a message printed by such a call stays `sent`, is never lost, and becomes `unacked` after the timeout. While the PM has a registered `wait` in progress, including a backgrounded one until it returns, the controller exempts it from stall timers, because Herdr shows the PM as `working` during the wait. Each `wait` is a tool call; the context cost per loop is measured in Stage 2.
- PM ack timeout: default 10 minutes. The timer does not run while the PM's Herdr state is `working` outside a registered `wait`, so a long PM turn does not send every printed message to `unacked`. Time spent inside a registered `wait` does count, because a PM that keeps looping in `wait` without acking is ignoring the messages it was shown, and Herdr shows the PM as `working` throughout every wait. Stall timers still skip registered waits (a waiting PM is not stalled); the ack and notification timers do not.
- Notification: if a PM message stays `queued`, `sent` or `unacked` for longer than `pm_notify_after` (default 5 minutes, not counting time while the PM's Herdr state is `working` outside a registered `wait`, like the ack timer; the deferral limit that applies to worker messages does not apply to the PM), the controller raises a `herdr notification` to the operator and repeats it every N minutes (default 10) while the queue is blocked. If `herdr notification` does not work, a pane the controller owns runs `cstan status --watch` (typing into an owned pane is safe) and rings the terminal bell. There is no automatic skip: a blocked PM queue waits for the operator.
- Optional enhancement, verified in Stage 2 and dropped if it fails: a `UserPromptSubmit` hook for the PM that runs `cstan inbox --peek` (a one-line count, marks nothing). It needs the operator's hooks excluded (`--setting-sources project,local`, with the Capstan hook added through `--settings`, because `--settings` alone merges with `~/.claude`), and that may also drop Herdr's own Claude hook. No `Stop` hook that adds context is used: it would force the PM to continue, which is controller-driven input.

**Message states.** `queued`, `deferred` (agent busy or blocked, or input line not empty; has a maximum deferral, after which a non-empty input line is handled as in the Workers rule above: the text is read and logged, the operator is notified, the line is cleared with `ctrl+u` and the message is then sent; a busy or blocked agent makes it `expired`), `sent`, `acked`, `acked_late` (an ack arriving after `unacked`), `unacked` (no ack in the timeout), `expired`, `cancelled` (the recipient's generation was replaced or the task ended), `failed`.

**Ordering.** Every unresolved state (`deferred`, `sent`, `unacked`, `expired`, `failed`) blocks later messages to the same recipient. Resolved states (`acked`, `acked_late`, `cancelled`) do not. Who resolves a blocked message: for a worker, the PM or the operator; for the PM, only the operator, because the PM cannot resolve a message addressed to itself. Resolution is a recorded decision: `retry` (an explicit resend), `skip` or `cancel`.

**No automatic resend, ever.** A resend can run an instruction twice, and pane reading is not a reliable trigger (E3, E4). Reading the pane after `unacked` is evidence shown to the PM or operator.

**Rules fixed by the controller core (PM-22, migration 0015).** These make the paragraphs above exact; nothing here relaxes them.

- **Timers are computed, not stored.** The controller records each change of an agent's observed Herdr state and each registered `wait` (open until it returns; the daemon closes it when the `cstan wait` connection drops). Timers are evaluated from those facts and the clock. For the PM ack and notification timers, time counts while the PM is not `working` and all time inside a registered wait counts. Stall time counts only while the agent is `working` outside every wait, measured from its last own command. An agent with no observation counts as not `working`.
- **Worker ack timeout.** A `sent` worker message becomes `unacked` after `worker_ack_timeout_seconds` (default 600) of wall-clock time, in `capstan.toml` under `[timers]`.
- **Resolutions.** `retry` returns a `deferred`, `sent`, `unacked`, `expired` or `failed` message to `queued` and restarts its notification clock; `skip` and `cancel` move it to `cancelled` and also apply to a `queued` message. A message addressed to the PM is resolved only by the operator. Every resolution is a recorded row.
- **Notification.** Only the head of a PM queue notifies; later messages are blocked behind it.
- **Record before send.** The driver records `recordSent` (and, for a non-empty input line, records the text with `recordInputClear` first) before it performs the physical send. A crash between the record and the send leaves the message `sent`; nobody acks it, it becomes `unacked`, and the PM or operator decides. The reverse order could send a message twice after a crash and is not allowed.
- **Generations.** An agent's actor changes with each generation: `replaceAgentGeneration` revokes the old actor, issues a new one, closes the agent's waits and cancels every open message of the old generation in one mutation. A token of an earlier generation fails in authentication.
- **Message bodies.** A body is plain text of 1 to 16384 bytes. Line feed and tab are allowed; carriage returns, escape sequences and other control, format and line-separator characters are refused, because the driver types the body into a pane and any actor with `message:send` could otherwise inject keystrokes. Zero-width joiners stay allowed so joined emoji sequences and non-Latin scripts work; Unicode tag characters (which can hide text and are the basis of subdivision flags) and lone surrogates are refused. Bodies may be multi-line, so the driver must deliver a body as one paste (the `herdr agent prompt` path pastes once and submits once), never as raw keystrokes, and only to a pane that is an agent interface; a pane that has dropped to a shell is a delivery failure, not a target. The audit trail holds only the body's hash.
- **Rejections.** An illegal transition, an ack by a non-recipient and a delivery of a message that is not the queue head are written to `message_rejections` and raised as an error; the same call replayed with the same idempotency key raises the same error.

**Stage 2e, first part: how the commands and the delivery driver behave (PM-25).**

- **Who may do what.** `inbox` and `send` are open to the operator and to agents; the core capability decides. An agent's `inbox` takes no argument. For the PM it pulls a `queued` head to `sent` and prints its `sent` and `unacked` messages; for any other agent it only prints those (an undelivered head is never shown, so it cannot be acked before it is typed). The operator's `cstan inbox <agent-id>` is a read-only peek that also shows a `queued` head. `send` takes an agent id or `@pm`: the operator and the PM may write to any active agent, every other agent only to the PM, and nobody to themselves. A body may be at most 15360 bytes (the adapter's 16 KiB text limit less room for the frame). `resolve <id> retry|skip|cancel` and `cancel <id>` are operator commands; a `retry` of a message that was `sent` or `unacked` prints a warning that the recipient may already have received it.
- **`wait`.** PM only. If the queue head is `queued` it is pulled at once. Otherwise the call registers a wait row and polls every 250 ms until the host's `wait_timeout_seconds` (default 90), re-printing the `sent` and `unacked` messages on return; a wait that has only such messages blocks for the full timeout, so time inside it counts for the ack and notification timers as section 5 requires. One wait per agent: a newer wait supersedes the older one, whose connection is answered `superseded`. A killed or half-closed client ends its row at once. The daemon closes any wait row still open at start, because a wait cannot outlive its connection. The client waits for the timeout plus 30 seconds at most.
- **Delivery driver.** One tick every 2 seconds (never under 500 ms): observe each agent that has a registered pane, apply the message timers, notify, then push worker messages one head at a time. Before it types it re-reads the ledger, so a message that was acked, cancelled or resolved in the meantime is neither recorded nor typed and leaves no rejection row. The frame is `[capstan message <id> from <role> (<agent-id>)]`, the body, and `Acknowledge with: cstan ack <id>`. A prompt Herdr refuses after the record leaves the message `sent`; the ack timer turns it `unacked` and the operator decides. Three consecutive real Herdr errors fail a message; a pane owned by another agent, a tainted pane or an unreadable input line skip it and, after ten ticks, raise a `delivery_stuck` notice (an agent with no registered pane is only logged, because PR 1 registers no panes). Text left in the input line is recorded before the clear keys are sent and the operator is told its length, never its text.
- **Notification.** Two channels: `herdr notification show` and a passive fallback that `cstan status --watch` shows with a bell. Each attempt appends a line to `.capstan/state/notifications.jsonl` (rotated at 5 MiB); the ledger's notification record is written when at least one channel succeeded. Herdr 0.9.1 answers exit 0 with `shown:false, reason:"disabled"` when notifications are off (a fresh isolated session), so the adapter treats that as a failure. Whether the operator's own session shows them was not checked.
- **Known limits of this part.** No pane is registered until the next part, so in production the driver delivers nothing yet; delivery is proved against a stub adapter. `wait` polls the ledger; an event-driven wake-up is later work. A `capstan.toml` that fails to load stops the daemon at start (and so `cstan start` and any command that starts it on demand) with the loader's message in the error and the daemon log. Configuration is read when the daemon starts; a change to roles, hosts, timers or notifications needs a restart, and `cstan config sync` needs the daemon stopped.

**Stage 2e, second part: launching agents (PM-25).**

- **Commands.** `cstan start` starts the daemon and, when `capstan.toml` exists, launches the PM. `cstan spawn <role>` starts one worker. `cstan pm restart` starts a new PM generation. They are daemon operator commands (the daemon owns the Herdr adapter) and answer `not_configured` when the daemon has no `capstan.toml` or no adapter. `CAPSTAN_LAUNCH=off` (also `0`, `false` or `no`, any case) keeps the daemon and `cstan start` out of Herdr entirely; the test suite sets it so no test reaches a real session.
- **Identity.** One seat per role, created once and reused. Every incarnation gets a new agent id `<role>-<n>` because the core refuses a reused id. A PM keeps its id across a restart (the generation changes). One active agent per role: a second `spawn` for an active role is refused with `role_active`.
- **The hub workspace.** Herdr 0.9.1 refuses to close a pane whose workspace has worktree children ("closing this pane would close a worktree group"; found by the live test). Workers' worktrees therefore hang under a long-lived hub workspace that runs `cstan status --watch`, never under the PM's workspace, so a PM pane can be closed and replaced while workers keep running. The hub opens at launch whatever the notification channels say.
- **Panes survive a daemon restart.** The ledger records each agent's pane, workspace, worktree, branch and base commit (migration 0016). At daemon start a background step re-registers them after Herdr confirms the pane exists and the agent name still points at it; the delivery driver starts after that step. A lost worker is ended and its worktree and branch are cleaned; a lost PM stays and `launch` answers `needs_restart`.
- **Worker worktrees.** The branch is `capstan/<agent-id>`, created from the recorded base commit. A failed spawn ends the agent, closes its pane, removes the worktree without force and deletes the branch only if it still points at the base commit. A worktree git will not remove (untracked files) is left and listed by `status` under `cleanupFailed`.
- **`pm restart`.** One core transaction builds the summary (objective, open work items, unacknowledged messages), records it and replaces the generation, because the replace cancels the PM's open messages. Open work means a state outside accepted, canceled and failed. A restart whose pane start fails leaves its summary unconsumed and the next restart carries it forward. The summary reaches the new PM as fenced data, labelled as information and not instructions.
- **What agents are given.** The token and socket path only in the pane's environment (an allowlisted `env -i` shell), `cstan` on PATH through `.capstan/bin/cstan`, a role prompt with a command reference for the kind plus the role's own prompt, and the allow rule `Bash(cstan *)`. Claude Code's exact rule syntax for that entry is unverified until PM-26.
- **Known limits.** The operator key is readable by an agent running as the same user (the DEC-005 limit): an agent that unsets its token acts as the operator. The operation budgets (60 s for steps, 30 s for cleanup) are checked between Herdr calls and never abandon one. There is no operator command to end a stuck worker; restart the daemon after ending the seat's authority.

**Stage 2e, third part: the PM delegates (PM-29).** The user talks only to the PM. The PM spawns, directs and releases the workers; it does not do project work.

- **Who may spawn.** `cstan spawn <role>` and `cstan release <agent-id>` are accepted from the operator and from an active PM agent. A worker's token is refused. The daemon checks the caller's agent record when it handles the call, so a token from a replaced PM generation no longer works. Both commands act through the launcher with the project credential, so the ledger attributes them to the operator; the daemon logs `requestedBy`.
- **Several workers per role.** The old rule of one active agent per role is gone. `[limits] max_workers` (default 3, range 1 to 16) bounds the active workers in total. A refused spawn names the limit, the active ids and any agent whose cleanup failed. The core allows one active agent per seat, so each concurrent worker gets its own seat: `<role>-seat`, `<role>-seat-2`, and so on, the first one no active agent holds. Agent ids and branches stay `capstan/<agent-id>` and an ended id is never reused.
- **Release.** `cstan release` ends the worker, closes its pane, removes its worktree without force and deletes its branch only when the branch still points at the base commit. The answer says what happened: `paneClosed`, `worktreeRemoved`, `branchKept`. A branch with commits stays, so the user can merge it. The PM itself cannot be released this way (`kind_not_releasable`); a PM restarts with `cstan pm restart`.
- **The PM prompt and tools.** The PM prompt says to delegate code, design and test work, never to edit project files and never to use Claude Code's Agent tool. A PM role without a `deny` list gets `Write`, `Edit`, `NotebookEdit`, `Agent` and `Task` denied; an explicit `deny` (even `deny = []`) replaces that. The change alters the role hash, so the next launch or spawn re-syncs it and a running PM needs `cstan pm restart`.
- **Starter roles.** `cstan init` writes pm, developer, designer, tester. A worker runs in `acceptEdits` mode, may use `git`, and may not run `git push`.
- **Known limits.** The deny rules and the prompt reduce what the PM does; they are not a sandbox. The PM can still reach files through Bash. `Bash(git push *)` does not match every spelling (`git -C . push`, extra spaces, `env git push`), and `Bash(git *)` also allows merge, checkout and branch deletion, so "never push or merge" rests on the worker prompt. A real sandbox is later work. Claude Code's rule syntax is verified in PM-26.

**Stage 2e, fourth part: where spawned workers appear (PM-30).** `capstan.toml` chooses it:

```toml
[layout]
spawn = "pane"          # "tab" (default): a Herdr workspace per worker; "pane": a split in the PM's tab
split = "auto"          # "auto", "right" (side by side) or "down" (stacked)
min_pane_columns = 60   # a split must leave both panes at least this wide...
min_pane_rows = 12      # ...and this tall
```

- **Mechanism.** The worktree is still made with `herdr worktree create` under the hub workspace. In pane mode `herdr pane move` then moves its pane into the PM's tab as a split; the emptied worktree workspace closes by itself. The moved pane gets a new pane id, and the ledger, the adapter registry and later adoption use that id. `release` closes the pane and removes the worktree as before. Verified by hand and by a live test on Herdr 0.9.1.
- **Which pane is split.** Among the PM pane and the active workers' panes in that tab (never the operator's own panes), the largest; ties go to the lower pane id by its numbers. With `auto`, a pane at least twice as many columns as rows is split `right`, else `down` (cells are about twice as tall as wide); the other direction is tried if the first would leave a pane under the minimum; a size that is not a positive integer, or a zoomed tab, counts as no fit. `right` and `down` are Herdr's own names.
- **A spawn never fails because of layout.** With no PM pane, a layout or move error, a zoomed tab or no room, the worker stays a tab and the answer says why (`placement: "tab"` and `placementNote`). A move that errors is checked again: the old pane still there means nothing moved; exactly one new pane at the worktree path means it moved; anything else fails the spawn, and cleanup then closes the one unregistered pane in the PM's workspace whose directory is the worktree (also after a crash in that window, when a recorded pane is gone and its row names a workspace other than the PM's). Limit: an operator shell in the PM's workspace at exactly that worktree path cannot be told apart from such a pane.
- **Limits.** After `cstan pm restart` the new PM opens its own workspace and workers already placed stay in the old PM's tab. Sizes are read once, when the worker is spawned. The starter file written by `cstan init` sets `spawn = "pane"`; a project without a `[layout]` table keeps tabs.

**Stage 3: facts (PM-31).** A worker reports finished work with `cstan report <commit> "<summary>"` (the full 40-character id, from `git rev-parse HEAD`; the summary is collapsed to one line of at most 1000 bytes).

- **What is checked.** By the daemon, from the ledger and git, never from the agent: the caller is an active Developer or Verifier agent (the PM and the operator may not report); the branch and base commit recorded for its current generation; that the commit exists, is an ancestor of the branch tip and is neither the base commit nor an ancestor of it (so it lies in base..tip; a commit the worker merged into its branch from elsewhere also lies there and is accepted). Reasons for a rejection: `no_branch`, `no_base`, `agent_changed` (the generation, branch or base changed between the check and the record), `commit_missing`, `not_new_on_branch`, `not_on_branch`. Git runs with argument arrays, a clean environment and `--no-replace-objects`, which closes the daemon's own environment and replace refs; the repository's own configuration, object alternates and branch refs stay writable by a worker (the DEC-005 hole). Only SHA-1 repositories are supported.
- **What is recorded.** Table `agent_reports` (migration 0017, immutable): the claimed identity (the actor behind the token, the agent and its generation), the commit, the branch, the summary, the verdict, the reason and the evidence the daemon checked. Rejected reports are kept too. A repeat of an accepted commit by the same agent generation writes nothing new (two identical reports racing each other can both reach the ledger once); at most 10 report commands a minute per agent and 100 rejected rows per agent generation. `cstan inspect <report-id> --json` shows one (kind `report`); the operator's daemon status lists the latest 20.
- **What the PM receives.** For an accepted report, a message whose sender is the controller's internal actor (the PM sees `from controller`, which a worker cannot send as) and whose text starts with `Verified report`, followed by controller-written facts and the worker's summary quoted and marked as not verified. It is queued in the same transaction as the report; a relay in the daemon queues it later when no PM was active. The PM prompt says a plain message from a worker is only the worker's word.
- **A branch per generation.** A spawned worker's branch is `capstan/<agent-id>-g<generation>`, checked with `git check-ref-format` before the worktree is created. Rows created before this change keep the name they hold. A later generation (Stage 6) starts from the base commit, not from the previous branch.
- **The known hole (DEC-005).** A process holding a stolen token that also commits into the worker's worktree is accepted. The gate run is in `STAGE3_GATE_RESULTS.md`.

**Stage 4, part 1: independent review (PM-32).**

- **Commands.** `cstan request-review <report-id> [role]` (the PM only) and `cstan review pass|findings "<text>"` (a Verifier agent only). The reviewer role is the one named, else the role called `reviewer`, else the only Verifier role in `capstan.toml`.
- **What happens.** The PM names an accepted report. The controller checks the request without writing, checks the commit exists, spawns a fresh reviewer of that role on a worktree and branch at the reported commit (a reviewer counts against `max_workers`), then in one transaction records the review (state `started`), checks independence and queues a task message from the controller's internal actor: the commit, the author's base commit, the diff commands, and the author's summary quoted and marked as not verified. The reviewer answers once with `cstan review` (the review is found by the reviewer's agent, so a replaced generation can still answer; an argument that is exactly `--json` or `--` is dropped by the CLI like for every command). The verdict text (up to 4000 bytes; CR, CRLF, NEL and the Unicode line and paragraph separators become LF; control and format characters, the zero-width joiner included, become spaces; cut with a marker if long) is recorded once and a controller message starting with `Review` goes to the PM, with the reviewer's text JSON-quoted and marked as the reviewer's opinion. About 750 ms after the reply the reviewer is released: agent ended, pane closed, worktree removed, branch deleted (it still points at the reviewed commit).
- **Independence.** A reviewer is always a new agent with a new actor and token. The ledger table `reviews` (migration 0018) has a CHECK that the reviewer's actor and agent differ from the author's, and the core refuses such a start before writing.
- **Rounds.** One review per request, one open review per report; at most 5 rounds that ended in a verdict per report (a cancelled round does not count; the state `failed` exists in the ledger but nothing writes it yet). A fix needs a new commit and a new verified report, then a new request.
- **Failure and recovery.** A failed spawn or a refused request costs no round. A reviewer that is ended or released before answering cancels its review in the same transaction. At daemon start, a finished review whose reviewer is still active gets the reviewer released. A verdict given while no PM is active is announced later by the relay.
- **Read-only profile.** `cstan init` writes a `reviewer` role whose `deny` list blocks Write, Edit, NotebookEdit, Agent, Task and git push; a Verifier role you write yourself has no default deny list (a tester must be able to write tests), so give a reviewer role its own `deny`. This is a tool-rule and prompt profile, not a sandbox: `Bash(git *)` still lets a reviewer run git against any worktree, the author's included. The gate run is in `STAGE4_GATE_RESULTS.md`.

**Stage 4, part 2: integration (PM-36).**

- **Commands.** `cstan integrate <report-id>...` (the PM or the operator), `cstan integrate confirm <integration-id>` and `cstan integrate discard <integration-id>`. `cstan request-review` also takes an integration id.
- **What happens.** Every named report must be accepted, named once, not already confirmed in an earlier integration, not in another merged integration that is still unsettled, without an open review, and its latest finished review must be a pass; one integration runs at a time. The controller records the base (the project's HEAD at that moment), the merge order and the branch `capstan/integration/<integration id>` in the ledger (migration 0019, tables `integrations` and `integration_reports`; the branch name is unique), then merges the commits one by one, each as its own merge commit, with `git merge-tree --write-tree` and `git commit-tree` (git 2.38 or newer), using its own git identity and a clean git environment. Nothing is checked out, so the plan's "separate integration worktree" is a repository with no worktree at all: no hook, filter, fsmonitor, signing or rerere setting of the repository is used. A commit already contained in the result so far is skipped; if every report is already in the base the integration fails. The branch is created at the result only if every merge succeeded.
- **Conflict.** A merge that reports conflicting files stops the run. The ledger records the state `conflicted`, the report and the files; the answer to the caller carries them, and when the operator asked, a controller message tells the PM. No branch stays; only unreferenced objects, which git collects. The controller never resolves a conflict; a developer resolves it as a new candidate, then report, review and integration repeat. A missing commit, a git failure, or every report already being in the base ends as `failed` with the reason.
- **Review of the merge.** The merged commit is reviewed through `request-review <integration-id>` by a new Verifier agent at that commit. The reviews table now has a second subject column; for an integration the ledger refuses (trigger) a reviewer who authored any merged report, and the core checks the same before writing. Rounds and verdict notices work as for a report.
- **Settling.** `confirm` needs a passed latest review, no open review and the merged commit already part of the project's HEAD when checked (the PM or operator merges the branch first; HEAD can still change after the check, which only matters if someone rewinds it); the controller then removes the branch. `discard` removes it; both are refused while a review of the integration is open. The branch is deleted only while it still points at the recorded commit and no worktree has it checked out. The time the merge finished stays in `completed_at`; settling is in the event log.
- **Recovery.** A branch that could not be deleted when an integration was settled is retried by the next integration in the same daemon run and swept at daemon start (all settled rows). An integration still `running` that this process is not merging (a cut-off run, or an outcome that could not be recorded) has its branch removed and is marked `failed` at daemon start and before the next integration begins.
- **Limits.** The controller does not push and does not merge into the project's HEAD. Conflict paths are read as NUL-separated names, one character per byte, and stored with every byte outside printable ASCII (and quote, comma, `#` and backslash) written as `\xNN`, so two different paths stay different and a path cannot spoof the PM's terminal; the stored paths are display text, not identifiers: at most 50 paths of 200 characters are kept (a longer one is cut between escapes and ends `...#` and twelve hex digits of a digest of the whole name) and the number left out is stored apart in `conflict_files_omitted` (a conflict list over 8 MiB of git output ends as `failed`). A repository with no commit, a SHA-256 repository or git older than 2.38 is refused with a reason. The merge result also depends on the repository's own merge and line-ending settings and attributes (renormalize, autocrlf, eol, rename limits); the controller does not override them. The same-user hole of DEC-005 applies: a worker can alter the repository's configuration, and a merge driver named in committed attributes and defined in the repository configuration can still run during `merge-tree`. The gate run is in `STAGE4_GATE_RESULTS.md`.

**Stage 5: supervisor and findings routing (PM-33).**

- **Why a new table.** The old `findings` tables (migrations 0001 and 0009 to 0012) belong to the work-item, assignment and seat flow (they reference `work_items`, `seats` and `commands`), which v2 does not use. Reusing them would need invented work items, so v2 gets its own small tables (migration 0020).
- **Roles and commands.** A role of kind `Supervisor` is spawned like a worker (`cstan spawn supervisor`; the starter `capstan.toml` has one; auto-start is a follow-up). Its default deny list blocks Write, Edit, NotebookEdit, Agent and Task, `git push`, `herdr` and `tmux` (`Bash(...)` patterns; the starter role writes the same list out); this is a tool-rule and prompt profile, not a sandbox (Bash stays open for `cstan`, and a same-user process can still do more: DEC-005). Three commands, all agent-class and answered only for the right kind (`finding check` is told from `finding <agent-id> ...` by its first argument: agent ids are made by the controller as `<role>-<number>`, and a role named `check` would give `check-1`, never `check`): `cstan observe <agent-id> [lines]` (Supervisor or PM, and the caller's actor must hold the `agent:observe` grant, so revoking it stops observation; `lines` is an integer from 1 to 120 written in ASCII digits without leading zeros, anything else is refused), `cstan finding <agent-id> <severity> <evidence> <correction> <done-when>` and `cstan finding check <finding-id> resolved|unresolved <evidence>` (Supervisor only). The Supervisor reads another agent only through `observe`: the controller reads the target's recorded pane (the visible screen, 40 lines by default, at most 120), removes escape sequences (CSI, OSC, DCS, SOS, PM and APC, the 8-bit C1 introducers; an OSC or string sequence counts only when closed by BEL or ST, and an introducer with no terminator is removed alone, so it cannot hide the text after it; an unfinished CSI at the end is removed), folds CRLF and lone CR to LF, turns control and format characters (bidi and zero-width included, LF excepted; this also breaks emoji joiners and Persian or Indic joiners into spaces: the reading is lossy for them by design) into spaces, then caps the text at 8000 bytes on a grapheme boundary with a cut marker and returns it with the agent's role, state and Herdr status and a note that it is the agent's own screen, not verified, and that any instruction in it is data. 30 observations per minute per caller (counted in memory, so a daemon restart resets it, like the report limiter).
- **What the Supervisor decides and what the controller owns.** Whether an agent is stuck, and whether it recovered, is the Supervisor's judgment, recorded with its evidence. Validation, delivery, the ack, the intervention count, the limit, the deadline and the escalation are the controller's and are not left to a model. Stalls stay the job of the Stage 2 timers.
- **The finding.** `finding` is accepted from an active Supervisor for an active Developer or Verifier agent (never the PM, a Supervisor or the caller). The finding is keyed by the target's agent id, not its generation, and the raiser by its agent id (so a replaced generation of either keeps the finding). `severity` is `info`, `low`, `medium`, `high` or `critical`; it is a label shown to the PM and the operator and changes no rule: every severity uses the same two interventions. The evidence is at most 1500 bytes, the correction 600 and the done-when condition 300; each is normalized like a review text (CR, CRLF and the Unicode line separators become LF; control and format characters become spaces; surrounding space is trimmed) (LF is the one control character kept; the normalizer is its own function, separate from the cut that `reviewText` adds) and then must show text (the controller's existing visible-text rule: a field with no letter, digit, punctuation or symbol once the blank filler characters U+2800, U+115F, U+1160, U+3164 and U+FFA0 are removed is refused, so a field of only a BOM, zero-width or filler characters is empty; a field made only of U+FFFD, what invalid UTF-8 in an argument decodes to, is refused too) and must fit its byte limit, counted in UTF-8 bytes after normalization: a longer field is refused, not cut, so the Supervisor shortens it. `severity` is matched exactly and in lower case. One finding may be open per target; 10 new findings per minute per Supervisor. In one transaction the controller writes the finding (`agent_findings`), the delivery (`agent_finding_deliveries`, attempt 1) and a message from its internal actor to the target. The message is controller text around three quoted fields: the finding id and severity, then the evidence, correction and done-when condition each JSON-quoted and labelled as the Supervisor's words (and the evidence as the Supervisor's reading of the screen, not verified), then "intervention 1 of 2". The target sees the quotes as data; this lowers but cannot remove the risk that an LLM follows text inside them (a listed limit).
- **Acknowledgement.** Message states are `queued`, `deferred`, `sent`, `unacked`, `expired`, `failed` (not final: the PM's or the operator's `resolve retry` puts `unacked`, `expired` or `failed` back to `queued`, and `resolve skip` or `cancel` ends one as `cancelled`) and `acked`, `acked_late`, `cancelled` (final). The finding counts as acknowledged when its latest delivery message is `acked` or `acked_late` (derived from the message state, not stored twice). `finding check` is refused until then. A delivery that stalls (`expired`, `failed`, `cancelled` by a resolution, never sent) leaves the finding open until the deadline below closes it. When a finding becomes final (`resolved`, `escalated` or `cancelled`), any of its delivery messages that is not final is cancelled in the same transaction, so a late retry cannot deliver a correction for a closed finding.
- **Resolution check and the two interventions.** `finding check ... resolved` ends the finding as `resolved` and records the check. `... unresolved` after the first intervention sends the second: a new delivery (attempt 2) with the new evidence and the original correction and done-when condition, "intervention 2 of 2". `... unresolved` after the second ends the finding as `escalated`. A third intervention is never made. The check evidence follows the same text rules as the finding fields (normalized, not empty, at most 1500 bytes, refused when longer) because it is quoted into the second message. Only the raising Supervisor agent may check.
- **Deadline.** A finding has no check by the raiser within `timers.finding_check_seconds` (default 1800, 60 to 86400) of the latest of its latest delivery's creation, the message's `queued_at` (a retry sets it again), `sent_at` and `acked_at` (deferrals and expiry do not count, so a busy or blocked target cannot hold the finding open): the controller ends it as `escalated` and records a check by its own actor with result `timed_out`. So the one-open-per-target lock always clears, whether the Supervisor stopped, the delivery never arrived or the target never acked. The sweep runs in the relay tick.
- **Escalation and notices.** `escalated` is a ledger state, listed by the operator's `cstan status --watch` (open and escalated findings with target, severity, intervention count and reason; an escalation rings the bell once) and by `cstan inspect <finding-id>`, whatever happens to messages, and queued to the PM as a notice. Notices (`raised`, `resolved`, `escalated`, `cancelled`) go to the PM through the message path from the controller's actor, in the transaction of the event when exactly one PM is active; with none or several the notice row waits (`agent_finding_notices`, message id set once) and the relay announces it when exactly one is active, bound to that PM's current generation, in insertion order per finding (so `raised` always precedes `resolved` or `escalated`).
- **Ending agents.** A finding is cancelled, in the same transaction as the end, when its target or its raising Supervisor ends. A correction already delivered is not retracted; queued messages to an ended target are already cancelled by the existing end logic. A restart of the target's generation changes nothing here: the message follows the messaging layer's rules and the deadline covers the rest.
- **Races.** Every transition (check, deadline sweep, end-cancel, notice announcement) is one controller transaction and updates conditionally (`WHERE state = 'open' AND interventions = N` and the like), so a loser is refused and two simultaneous unresolved checks cannot create two second deliveries. A notice's message and its message id are written in one transaction.
- **Ledger rules.** `agent_findings`, `agent_finding_deliveries`, `agent_finding_checks` and `agent_finding_notices` are append-only except the finding's state (`open` to `resolved`, `escalated` or `cancelled`, then final), its intervention count (1 to 2) and a notice's message id (set once).
- **Tests the plan requires.** Refusals (wrong caller kind, bad target kind, the PM or the caller as target, text rules, second open finding, rate limits, check before ack, check by another agent, check after final); the full resolved path; the two-intervention path to escalation and the refused third; delivery that is cancelled, expired or failed then the deadline; replaced generation of target and raiser; cancel on end of target and of raiser; no PM, two PMs and the relay; the observe sanitizer and caps; ledger immutability triggers; migration data and the status listing.
- **Limits.** A looping agent usually shows as `working`, and the messaging layer sends nothing into a working pane: the correction stays deferred, may expire, and the finding then escalates at the deadline with nothing delivered. That is a visible outcome (the escalation reaches the operator) and not a silent one, but the loop is not interrupted; an interrupting delivery is a follow-up. A retry by the PM or the operator restarts the deadline, so repeated retries can keep a finding open; they are human actions and are recorded. The Supervisor is an agent: whether it notices a loop is not guaranteed by the controller, and its observation is a screen reading, not a tool trace. Independence of the Supervisor from the workers is by convention only. The gate uses the fake Claude stand-in and is in `STAGE5_GATE_RESULTS.md`.

**Stage 6: recovery (PM-34).**

- **What already exists.** A daemon start adopts the panes in the ledger, closes stale waits, recovers running integrations and reviews, and ends agents whose pane is gone (the Stage 2 gate saw the last happen only at the next start). A message is recorded as `sent` before it is typed and is never resent by the driver, so delivery is at most once. `cstan pm restart` replaces the PM generation from a ledger summary. This stage adds what the Stage 2 gate found missing and checks the whole against an oracle.
- **Liveness.** The delivery driver already observes every active agent on each tick. When an agent's observation fails with a Herdr error whose code is `agent_not_found` or `pane_not_found` (the Stage 2 gate saw `agent_not_found` for a closed pane), the driver counts it; three failures in a row (about six seconds at the default tick) mean the agent is lost. A successful observation resets the count, and so does any other error (a pane mismatch, a Herdr server that does not answer, a timeout, a session, workspace or tab not-found): not knowing is not seeing it gone, so those are not a loss and break the row. When every active agent that has a registered pane fails with not-found in the same tick and there are at least two of them, nothing is counted and the counters are held, not reset, for at most ten such ticks in a row (after that every counter is reset to zero and counting starts again, so panes that really closed together are still reported after three more failures, and a Herdr restart longer than that is a listed limit) (a Herdr server that restarted would otherwise make every live agent look dead; with a single agent that case is not told apart and is a listed limit). A counter is dropped when its agent ends or is replaced. A lost agent is recorded once per generation as a ledger event (`agent.lost`, no schema change; the core looks for an earlier event of the same agent and generation in the ledger before it writes, so a daemon restart cannot report it twice) and the PM gets one controller message (the PM's queue is pulled, never pushed, so a failed delivery cannot block it); the event and the message are written in one transaction naming the agent, its role, the branch it held and the messages that were not acknowledged. Nothing else happens by itself: the agent stays `active` in the ledger, its deliveries keep failing as before, and `cstan status --watch` lists it as lost for as long as the driver sees it failing: a later successful observation clears it (the ledger event stays), and so does the end of the agent. A PM that is lost is shown to the operator the same way (log and watch); the operator restarts it. The controller never replaces an agent on its own, because an automatic restart could execute work twice.
- **Replacement.** `cstan replace <agent-id>` (the PM or the operator; workers only; refused while an integration is running; a second replacement of the same predecessor is refused because the ledger already holds `agent.replaced` for it; that event is written, naming predecessor and successor, in one transaction that checks for an earlier one, only after the successor has started, so a failed spawn leaves no event and the replacement can be run again; the launcher serializes operations inside one daemon, and a crash after the spawn and before the event leaves the successor active and the predecessor replaceable once more, which the PM sees in `cstan status` and resolves by releasing one of them) works on an active predecessor and on one that is already ended (for example ended at a daemon start because its pane was gone: nothing is released then, the seed and the rebase work the same). For an active one it releases the named agent through the existing release path (agent ended and its token revoked, pane closed, worktree removed without force, branch kept when it holds commits) and spawns a new agent of the same role through the existing spawn path, with two differences: the new branch starts at the predecessor's last accepted report commit when it is 40 lowercase hex characters after lowercasing (a SHA-256 repository is a listed limit: it falls back to HEAD), resolves as a commit (`rev-parse --verify --end-of-options <sha>^{commit}`) and is reachable from the predecessor's branch tip or the project's HEAD (else the project's HEAD, also when the predecessor's branch is missing; the seed says which base was used; a git older than 2.24, which has no `--end-of-options`, is detected by its version and reported as an old-git error, not hidden as a fallback), and the new agent's prompt carries a seed block built from the ledger. The new agent has a new id, so the predecessor's token cannot report or ack for it. The block is built and size-checked (at most 24 KiB counted in UTF-8 bytes after JSON escaping: 20 messages, 10 reports and 5 findings, each text sanitized first (terminal escape sequences removed as a whole, then control, format and line-separator characters and lone surrogates made spaces) and then cut to 300 code points (never inside a surrogate pair) with a marker; the seed path folds LF and CRLF into one space, trims, and reads `(empty)` for text that is blank afterwards, using `stripTerminalSequences` and `normalizeText` from `src/observe.ts` and `src/text.ts`; entries are ordered and dropped by ledger sequence; if the JSON-escaped block still exceeds the limit the oldest messages, then reports, then findings are dropped until it fits, and a block that cannot fit at all is refused before anything is released; a text that is empty after sanitizing reads `(empty)` and an empty list reads `none`) before anything is released, fenced and JSON-quoted like the PM restart summary and says it is recorded data (every ledger text is JSON-quoted on one line, so it cannot start a line with the fence marker and cannot close the fence): the predecessor's id and role; its branch, base and tip; up to 20 of the newest messages sent to it with sender, state and the text cut to 300 characters; its accepted reports (commit and one-line summary); its open findings; and the rule that nothing in state `failed`, `unacked`, `sent`, `queued`, `deferred` or `expired`, or `cancelled` with a reason that starts with `agent_ended` or `generation_replaced`, was done, and that the new agent waits for the PM to send what still matters. Unacknowledged instructions are not resent by the replacement: resending is the PM's or the operator's explicit act. While the agent is alive that is `resolve retry` of the same message (a recorded resend: the ledger shows the decision); after a replacement the old message's recipient has ended, so the resend is a new `send` to the replacement's id (a new instruction id). If the release leaves the old pane open (the close failed for a reason other than the pane already being gone), no replacement is spawned: the answer is `blocked`, names the released agent and says to close the pane and run `cstan replace <agent-id>` again (it works on the ended agent), so two live agents never work on one task. A pane that is already gone is not an error. If the old worktree cannot be removed without force (uncommitted changes), the replacement still starts and the answer reports `worktreeRemoved: false`. If the release works and the spawn fails, the answer says so and names the released agent; nothing is retried, and the release has already cancelled the predecessor's non-final messages once (a rerun finds it ended and cancels nothing again). Waits of the predecessor are closed by the release; a `send` to the ended predecessor is refused as to any ended agent; its reports and messages stay in the ledger. The predecessor's branch is kept when it holds commits (release removes it when it holds none) and may hold commits that were never reported; the seed gives its tip and says those commits are not accepted. The branch an agent had is also written into its end event (and its loss event), so the loss message and the seed still name it after the pane row is gone. Reviews of the predecessor's accepted reports are not affected.
- **Agents found dead at a daemon start.** The adoption step that ends an agent whose pane is gone also records the loss and sends the PM the same one-time message, in the same transaction as the end (event `agent.lost`, reason `found_dead_at_start`), so a restart does not hide a loss and a crash cannot lose it. The loss is deduplicated by agent and generation whatever its reason. `cstan replace` then works on that ended agent.
- **Failed messages.** This stage changes the code that cancels an agent's messages (`#cancelMessagesOf`; today it cancels every message that is not `acked`, `acked_late` or `cancelled`, `failed` ones included, and overwrites the reason). Ending an agent (`release`, which `cstan replace` uses, and the daemon start's cleanup of an agent whose pane is gone; a lost agent that is still running is not ended) now skips `failed` messages: they stay `failed`, also when `cstan replace` ends the predecessor; and `resolve retry` is refused for a message whose recipient has ended (`recipient_not_active`), before any decision row is written (so a refused retry is not counted as a recorded resend), while `skip` and `cancel` still work, so an operator can clear them. Replacing a PM generation (`pm restart`) keeps cancelling `failed` ones, because the same agent id goes on and a failed head would block the new generation. Messages that stay `failed` stay in the unresolved list until an operator or PM resolves them. A `failed` message that is cancelled by an explicit resolution (`skip` or `cancel`) or by a PM restart ends `cancelled` with the failure kept in its state reason (`<resolution reason> (was failed: <failure reason>)`; the failure reason and the resolution reason are each sanitized in the same way to one line of at most 200 code points, and each reads `(none)` when empty; it cannot nest, because a retry clears the reason and a new failure sets a fresh one), so the final row still shows what happened; a retry from `failed` clears the reason, and the history of every transition stays in the event rows. The queue of a recipient is by agent id, so a replacement under the same id would be blocked by a failed head; that is one more reason replacement uses a new id.
- **Stale reports.** A command carrying the predecessor's token is refused as unauthenticated once the predecessor has ended; a report by the replacement of a commit that lies only on the predecessor's branch is refused as `not_on_branch`; both are tested.
- **Crash and restart.** The existing recovery is exercised, not changed: a daemon killed after a message was recorded as `sent` and before or after it was typed leaves the message `sent` and never types it again; an agent whose pane died while the daemon was down is ended at the next start as before; reviews and integrations that were running are recovered. The harness and the live gate check this against the oracle.
- **Failure-injection harness.** A test harness (`test/recovery-harness.ts`) wraps the delivery path with a stand-in agent that records every physical delivery by instruction id (the message id), and a fault plan: close the pane, make observation fail with a given Herdr error, make the typing step fail, stop the world between the record and the typing, and reopen the controller on the same ledger. The oracle: the number of physical deliveries of an instruction id is at most one plus the number of `resolve retry` decisions the ledger holds for it, and in the harness, where the fault plan says which sends were typed, exactly the number of typed sends. It is zero when the ledger says the message was cancelled before it was typed, or when the message is `sent` and ended `unacked` after a crash between the record and the typing (the recorded loss of an at-most-once delivery). Every id with a delivery has exactly that many lines. The harness counts by the ledger's event rows (the `sent` transitions and the `resolve retry` decisions), not by the final state, because a release later turns a stuck message into `cancelled`.
- **Gate.** The fake Claude stand-in learns to append the id of every message it receives to a file (one line per id, written with one `O_APPEND` write; the checker strips a BOM and CR, skips empty lines and matches whole ids; a partial last line is a failure unless the stand-in was killed, which is the case after a pane close, and then only that last line is ignored; leading and trailing whitespace of an id line is trimmed). In a live run (one id file per agent, so a torn last line of the predecessor cannot join the replacement's first id): instructions are sent, the daemon is killed with `kill -9` after one was typed and before it was acknowledged and restarted (it is not typed again), that instruction is resent with `resolve retry` (two lines for it), the worker's pane is closed, the loss message arrives, `cstan replace` runs and a new instruction is sent to the replacement. Oracle: the rule above for every instruction id, and the predecessor's token cannot report. The run is in `STAGE6_GATE_RESULTS.md`.
- **Limits.** A Claude process that exits while its pane stays open is a loss only if Herdr then reports the agent as not found; an agent that is alive and silent is the stall timer's and the Supervisor's. Delivery is at most once, so a crash between the record and the typing loses the message (it ends `unacked`, visible); it never duplicates it. The seed block is data written by other parties and the replacement may misread it; the controller does not verify what the replacement does with it.

**Stage 7: Codex and OMP hosts, and removal of Docker (PM-35).**

- **Probes (real CLIs, Codex 0.159.2 and OMP 18.3.1, no model turn unless stated).** Both start under `herdr agent start --kind codex|omp` and Herdr reports `idle`/`done` and `working` for them. Codex shows a trust dialog for a folder it has not seen (`Folder access`, the path, `› 1. Trust and continue`, `2. Quit`; Herdr reports the agent as blocked); OMP shows none. The input line is `› <text>` in Codex (the placeholder `Ask Codex to do anything` is dim; further lines of typed text follow, then the status line, which starts with a coloured span) and the last line `╰─ <text>` in OMP. `Ctrl+U` clears the input in OMP and one line at a time in Codex (the existing clear loop reads again after each key). **A Codex worker cannot reach the daemon socket in any restricted sandbox mode:** `connect` returns EPERM under `workspace-write` (also with `network_access=true`) and under `read-only`, and succeeds only under `danger-full-access`; the permissions-profile route for Unix sockets could not be made to work in the time spent and is not used.
- **Host profile.** A new module `src/herdr/hosts.ts` holds one profile per kind (`claude`, `codex`, `omp`): the start arguments for a role, the input-line parser and the trust-dialog parser. The adapter and the launcher take the profile from the role's host kind instead of the literal `"claude"`; the pane entry records the kind; `extractInputLine` and `parseTrustDialog` keep their Claude behaviour and the profile selects the Codex or OMP parser. The delivery path, the driver and the ledger are not changed: a message is still typed with `herdr agent prompt`.
- **Codex arguments.** `--sandbox danger-full-access --ask-for-approval never`, `--model` when the role sets one, `-c check_for_update_on_startup=false` (so the update prompt does not appear), `-c projects."<worktree>".trust_level="trusted"` (a run-time override that skips the trust dialog without writing the operator's `~/.codex/config.toml`; the dialog handler below stays as the fallback), and the role prompt as `-c developer_instructions="<TOML basic string>"` (newlines escaped as `\n`, so no argument holds a newline). The role's `permission_mode` is not translated; see the rule below.
- **Codex argument details.** The trust key uses the worktree's real path (symlinks such as `/tmp` resolved) with TOML escaping of `"` and `\\`; the gate proves no dialog appears for a worktree under a symlinked path. The prompt string escapes `\\`, `"`, `\n`, `\r`, `\t` and every other control character as `\\uXXXX`. A prompt whose escaped argument passes 120 KiB is refused at launch (one argument may not pass about 128 KB); a role prompt in `capstan.toml` is at most 64 KiB, so only a long seed can reach that limit. Tests cover `startAgent` for each kind, including a Codex start that returns `agent_not_ready` and is then routed to the Codex dialog parser (the adapter's literal `"claude"` kinds are removed).
- **Existing behaviour kept.** Prompt files are written by the adapter into its own temporary directory (mode 0600, outside every worktree) and removed by `close()`, as for Claude. **Grouping agents by project in Herdr (PM-42).**

- **Facts from the Herdr 0.9.3 docs and CLI.** Agent names must match `[a-z][a-z0-9_-]{0,31}` and are unique among live agents of one server (a session); the name follows the pane's occupant and is cleared when the agent exits. `herdr agent rename <target> <name>` names an agent that is already running (the docs rename by pane id). A workspace has a label (`workspace create --label`, `workspace rename`); a worktree workspace nests under its parent in the Spaces panel. `pane report-metadata` and `workspace report-metadata` take `--source ID` and `--token NAME=VALUE` (display only, optional `--ttl-ms` and `--seq`; text is capped at 80 characters); the sidebar rows are configured by the operator in Herdr's own config (`ui.sidebar.agents.rows`, default `[["state_icon","machine","workspace","tab"],["agent"]]`, and `ui.sidebar.spaces.rows`), and a row may name a `$name` token that a report set. The default `herdr_session` is `default`, the operator's own session, so every project's agents share one namespace today.
- **Problem.** Capstan names the PM workspace `capstan-pm` and the watch workspace `capstan-watch` in every project, labels a worker's workspace with its bare id (`developer-6`), and gives Herdr the ledger id as the agent name (`pm-1`, `developer-6`). Nothing says which project an agent belongs to, and a second project in the same session cannot start its own `pm-1`.
- **Project label.** The project's display name is `[project] name` from `capstan.toml` when set, else the base name of the project directory. Its slug is that name lower-cased, every run of characters outside `a-z0-9` replaced by one `-`, trimmed of `-`, prefixed with `p` if it starts with a digit, and cut to 10 characters (trailing `-` trimmed). An empty slug is `p`.
- **Agent names.** The name Herdr sees is `<slug>-<agent-id>`; the ledger, the commands and the prompts keep the bare id. The adapter takes the slug as an option and translates at every Herdr call that carries an agent name (`agent start`, `agent get`, `agent prompt`) and when it reads a name back; callers still pass the ledger id. A name that would pass 32 characters is refused at start with the reason. The adapter checks the full name against Herdr's own rule `[a-z][a-z0-9_-]{0,31}` (its existing, wider `NAME_PATTERN` is for labels and branch parts and is not used for agent names). Config load refuses a role name longer than 16 characters, which is what `10 + 1 + role + 1 + 4 digits` leaves for ids up to 9999 (a role name of up to 32 characters was valid before, but a name that long never fitted Herdr's own 32-character limit once the `-<n>` suffix was added).
- **Workspace labels.** `<project> · pm` for the PM workspace, `<project> · watch` for the watch workspace, and `<project> · <agent-id>` for a worker's worktree workspace, which still hangs under the watch workspace, so the Spaces panel shows one group per project. The project's display name is cut to 24 characters for labels and tokens, and a label is free printable text of at most 64 characters (the adapter's current label rule, which allowed no space or dot, is widened for labels only).
- **Metadata.** After a pane's agent starts, and for each workspace the adapter creates, the launcher reports `project`, `role` and `agent` tokens with `--source capstan`. A failure is logged and never fails a start (the data is display only).
- **`cstan herdr-config`.** Prints a snippet for Herdr's own config that adds `$project` to the agent rows and the space rows, with a comment saying where to paste it. Capstan never writes Herdr's configuration. Whether Herdr accepts the snippet is checked live at the gate; the command says so in its output if it could not check.
- **Upgrade without losing running agents.** When the daemon adopts a pane and Herdr has no agent under the new name, the adapter looks the old bare name up; if it is on the same pane it runs `herdr agent rename <pane> <new name>` and adopts it. Nothing else about adoption changes. A bare name that is on another pane is a mismatch, as today. Adoption also renames the agent's workspace to its new label (`herdr workspace rename`, best effort), so an upgraded project does not keep `capstan-pm` and `capstan-watch`.
- **Oracle.** Unit tests for the slug, the name and its length limits, the translation at each Herdr call, the labels, the metadata calls (and that a failure is not fatal), the rename-on-adopt path and the config refusal. A live gate in an isolated Herdr session runs two projects, each with a PM and a worker, at once: no collision, the sidebar shows the project in each label, the metadata is reported, a daemon restarted on a project whose agents carry the old names renames and adopts them, and `herdr agent list` shows `<slug>-<id>` names. The default Herdr session is compared before and after.
- **Limits.** Two projects whose names slug to the same ten characters still collide in one session; the second start fails with Herdr's name error and the hint to set `[project] name`. Herdr's UI templates are the operator's to set: without the snippet, the labels and names already carry the project, and the tokens add nothing visible.

**One workspace per project, PM on the left (PM-43).**

- **What the operator asked for.** (1) One row per project in the Spaces tree with everything under it, instead of `pm` and `watch` rows side by side. (2) More room for the PM, always on the left, never split top and bottom. (3) When the right column is full, a worker opens as a tab, as it does today. The operator confirmed these three choices in a picker; the PM width is 60%.

Closing the PM's pane is allowed when the workspace still has another tab (and when it has another pane). `herdr pane split` and `herdr pane move` take `--ratio`, the fraction the original pane keeps (a split of a 174-column pane at `0.4` left it 70 columns). `herdr tab create --workspace ID --label TEXT` adds a tab with its own root pane.

## 6. Facts are verified, not trusted

An environment-variable credential only labels a reporter. Any same-user process can read it and forge acks and reports (E5). The controller narrows what a forger can do; it does not close it:

- A reported commit must exist on the branch recorded for that agent's current generation; the generation must be current; the state transition must be legal; acceptance needs an independent reviewer receipt bound to that exact commit.
- Not closed: a process holding a stolen token that also has a valid commit on that branch is accepted. Any same-user process can commit into any worktree. This is a known hole (DEC-005), and the Stage 3 gate records it as a documented limit, not as a pass.
- Tokens are per agent and per generation and are never printed. The ledger records the claimed identity together with the evidence that was checked.

**Operator authority and the control channel.** `cstan` reaches the daemon over a Unix socket in the state directory (mode 0600). Any process of the same user can use it. Agent commands (`report`, `ask`, `ack`, `inbox`, `wait`, `request-review`, `finding`, and the read-only `status`) need the agent's token. Operator commands (`assign`, `cancel`, `send` as the operator, `pm restart`, resolving a blocked message) need an operator credential that is not put in any agent's environment. Each role's profile carries host deny rules for the operator commands. The read-only commands are usable with either credential: an agent, including the PM's optional hook, uses its token for `status` and `inbox --peek`; the operator and the controller-owned `cstan status --watch` pane use the operator credential in read-only mode. Both controls are only as strong as the same-user boundary: an agent that reads the operator credential file, or ignores its deny rules, can forge the operator's authority. This is a listed residual risk, not a solved problem.

## 7. Herdr state is a hint

With the installed hook, the idle and blocked states that were explained came from screen-detection rules with a remotely updated manifest (E3). Herdr state decides when to send and spots `blocked`. Stalls (`working` with no receipt and no registered wait for a configured time) are detected by controller timers from Stage 2, not by the Supervisor, and reported to the PM and operator. Nothing that matters relies on Herdr state alone. Pinning or disabling manifest auto-update is an open item; a Claude Code, Herdr or manifest update is a revisit trigger (DEC-005).

The Herdr adapter (`src/herdr`, Stage 2d) is the only code that types into a pane. Facts it relies on, all probed against Herdr 0.9.1 in an isolated session (`TESTED_HERDR_VERSION`; another version is a revisit trigger):

- The session is always named (`herdr --session NAME`, `HERDR_*` removed from the environment), so the operator's default session cannot be reached by omission.
- Herdr reports a failed command as JSON on stderr with a non-zero exit; `agent start` needs a timeout of about 5 seconds or more and reports `agent_not_ready` when the agent is blocked at the trust dialog, which the adapter reports as `blocked_at_startup`.
- Every pane is registered with a role and a phase. A PM pane accepts only its launch; after that no send, clear or dialog answer reaches it. An unregistered, fresh or tainted pane accepts nothing.
- A guarded send delivers only when the agent state is `idle` or `done`, the input line is readable and empty, and the state is still idle after that read. The caller's record runs before `agent prompt`, and a failing record sends nothing. Every other case is a deferral with a reason.
- Clearing text a user left in the input line needs the maximum deferral to have elapsed and an idle agent. The text is handed to `discard` and each key is logged before it is sent. Up to five `ctrl+u` rounds run; a line that does not clear is `ClearFailed`.
- The trust dialog is answered only for a worker pane whose worktree path equals the dialog path, with exactly the options `No, exit` and `Yes, I trust this folder`. Enter is sent only after a second read shows the trusted option selected.
- Agent shells start with `env -i` plus an allowlist, and an agent cannot be started in a fresh pane without one; the token is delivered through a 0600 file that the new shell deletes, so it never appears on the command line or the screen.

Herdr trims trailing whitespace from a screen read, so an input line holding only spaces looks empty and a message may follow those spaces. Herdr sends a message that starts with a dash, and a multi-line message, as text (`--` is not supported by `agent prompt`).

Not verified: `ctrl+u` on a multi-line input in real Claude Code (the stand-in models it), and the `done` state. The delivery driver, pane re-registration after a restart and surfacing `PromptUnrecognized` belong to PM-25.

## 8. Permissions and how agents learn the commands

- **Per-role profile** in `capstan.toml`: host, model, permission mode, allow and deny rules, and for workers `-- --settings '{"disableAllHooks":true}'` so the operator's own hooks (claw8) do not interfere (verified in the spike's additional finding on global Claude configuration). Turning hooks off also drops guards the operator may want, and the rest of `~/.claude` was not examined. Auto permission mode is off for spawned agents unless the profile says so; an agent that inherits auto mode runs commands without asking.
- **`cstan` is allow-listed per role.** In default permission mode a command outside the allow rules prompts (E3). The agent learns the commands from a role prompt passed with `--append-system-prompt`. Both are verified in Stage 2, before anything depends on `ack`.
- **Confinement.** `--add-dir` adds directories; it does not limit an agent to one. Confinement to the worktree relies on the working directory plus per-role allow and deny rules for writes, and holds only as far as the host enforces them. This plan claims no more.
- **Prompts.** A permission prompt makes the agent `blocked`. The controller notifies the operator. The PM never answers permission prompts. Nothing presses Enter on a prompt without reading it: the trust dialog defaults to "No, exit" and the permission prompt defaults to "Yes" (E1, E3).
- **Trust dialog exception** (DEC-005): the controller may answer the startup trust dialog for a worktree path it has just created, after reading that the dialog names exactly that path and choosing the option by its text. This is a screen-driven keypress, so it is scraping and it is logged. Pre-trusting through the host's configuration is preferred if it works.

- **Agent environment (requirement for the Herdr adapter).** A pane started through Herdr gets the environment of the Herdr server, not of the daemon. The adapter builds an allowlisted environment for every agent and sets `CAPSTAN_TOKEN` and `CAPSTAN_SOCKET` explicitly, per agent and per generation. The daemon removes both variables from the environment of the process it spawns, so a daemon started from an agent pane never carries an agent token. **Passed variables (PM-37).** The allowlist is fixed (PATH, HOME, USER, LOGNAME, LANG, LC_ALL, TERM, TMPDIR); anything else an agent needs, such as an API key for an MCP server, is named by the operator in `capstan.toml` under `[env] pass = ["NAME", ...]` (up to 32 upper-case names; `CAPSTAN_*`, names Capstan already sets (PATH, HOME, USER, LOGNAME, LANG, LC_ALL, TERM, TMPDIR) and names that change how a shell or loader behaves (IFS, PS0, PS1, PS2, PS4, PROMPT_COMMAND, BASH_ENV, ENV, SHELLOPTS, BASHOPTS, GLOBIGNORE, HISTFILE, CDPATH, ZDOTDIR, SHELL, PYTHONSTARTUP, PERL5OPT, NODE_OPTIONS, and any name starting `LD_`, `DYLD_`, `GIT_` or `BASH_`; this guards against accidents in a file the operator writes and is not a boundary: other interpreter variables such as PYTHONPATH can be listed) are refused). The launcher copies each listed variable that is set in the daemon's own environment into every agent it starts (the PM, workers and reviewers; not the watch pane), unchanged. The daemon's environment is the environment of the shell that ran `cstan start`, so a variable defined only in an interactive shell file the daemon's shell did not read is absent. A listed name that is not set there is reported: the answer of a launch, spawn or PM restart that started an agent carries `missingEnv` and a `warning` (the CLI prints it), and the daemon log has an `env_pass_missing` entry with the names for that operation; an operation that started nothing reports nothing. A value that is not acceptable text (any control or format character, so a multi-line value such as a PEM key is refused) fails the launch naming the variable, never the value. A listed variable that is set but empty counts as not set (it is reported and not passed); one whose bytes are not valid UTF-8 reaches the daemon with replacement characters and is passed that way. Values are never logged or printed. The list is project-wide, not per role, and is as trusted as the rest of `capstan.toml` (it already names the command each host runs).

## 9. Recovery, roles and persistent agents

- **PM failure and takeover.** The controller runs without the PM. `cstan pm restart` (Stage 2, with the slice) starts a new PM with a summary rebuilt from the ledger: objective, decisions, open work, unacknowledged messages. The operator can always act through `cstan` directly (`status`, `assign`, `cancel`, `send`, `inbox`).
- **Persistent agents.** An agent lives until the task ends. Its assignment holds many rounds (an instruction, then a report). A replacement happens only on failure and is seeded from the ledger. Automatic recycling for heavy context is out of the slice.
- **Roles from configuration.** `capstan.toml` gives each role a free name and one of four kinds: `PM`, `Developer`, `Verifier` or `Supervisor`. The kind decides the capabilities. `src/controller/types.ts` fixes six roles (`operator`, `controller` and the four kinds), `src/controller/auth.ts` checks that list, six tables carry it in CHECK constraints, and `src/controller/core.ts` hard-codes role names (the literal `Verifier` appears 37 times, including in acceptance and final-verification logic), so open role names are not possible in this slice. Migration 0014 (PM-21) adds one table, `role_definitions` (role name, kind, host, config hash, state), filled by `cstan config sync` through an audited controller mutation. A seat created from a role stores the role name in `seats.name` and the kind in `seats.role`; work items keep `required_role` as the kind, so two roles of one kind are told apart by their seat. `auth.ts` and every existing table are unchanged. A role whose capability set matches no kind needs a per-actor capability grant or a later migration that rebuilds the CHECK constraints. The `agents`, `messages` and `rounds` tables come with the tickets that use them. The slice defaults are `pm`, `developer` and `reviewer`; `supervisor` is added in Stage 5.
- **Review evidence contract.** Review acceptance reuses DEC-004's candidate-evidence rules: verifier evidence carries a pass value, a non-empty artifact reference and an exact criterion string from the accepted input snapshot, bound to the exact candidate commit. How the PM supplies the acceptance criteria through `cstan` is a Stage 3 to 4 design item.

## 10. Worktrees, branches, review and integration

- **Branches.** Named `cap/<task>/<agent>-g<generation>`. A branch belongs to one agent generation. After a replacement, the new generation gets a new branch created from the last accepted candidate, or from the old branch tip only if the ledger records that tip as the resume point. "The agent's branch" always means the branch recorded in the ledger for the current generation.
- **Reviewer.** `cstan request-review` makes the controller create a worktree on a review branch at the given commit (`herdr worktree create --base <commit>`), start a reviewer there with a read-only profile, and remove the worktree and branch after the report. Findings come back through `cstan report`. The reviewer is never the author's session (controller-enforced). One review round per request.
- **Integration.** A controller operation in a separate integration worktree. The base is the main branch head at the time of integration, recorded in the ledger; the merge order is the order the PM recorded in the ledger. A conflict blocks and is reported to the PM; the controller never resolves it with a model. A developer may be assigned to resolve it as a new candidate. The integrated commit is re-verified by a reviewer before acceptance.
- **Cleanup.** Worktrees are removed at task end or on cancel (`herdr worktree remove`). Branches are kept until the PM or operator confirms deletion.
- **Supervisor (after the slice).** Always on, read-only by permission profile, watching through `herdr agent list/read/wait` and controller digests, reporting through `cstan finding`. Only the controller sends input to, starts, stops or closes agents; read-only inspection commands (`agent list`, `agent read`, `agent wait`) are allowed for the Supervisor and for diagnosis. The controller routes findings through the same message path. Independence is by convention only.

### Stage 2 gate

Results of the run on real Claude Code sessions are in `STAGE2_GATE_RESULTS.md` (PM-26).

Run on real Claude Code sessions in an isolated Herdr session. Every case names its oracle.

- (a) 10 consecutive PM to developer rounds with every message answered exactly once (oracle: one answer per message id in the transcript, and `acked` for each in the message log).
- (b) with text already in a worker's input line the message is deferred, then delivered without merging (oracle: received text equals sent text); or, after the maximum deferral, the operator is notified, the text is logged, the line is cleared and the message is then sent (oracle: the log holds the text and the notification, and the received text equals the sent text).
- (c) a message queued while the agent is `working` is not sent until `idle` or `done` (oracle: send timestamps against recorded Herdr state history).
- (d) killing the developer's pane mid-round leaves the message `unacked` or `cancelled`, never silently lost, with no resend (oracle: message log).
- (e) `pm restart` writes a summary for the new PM from the ledger, and the new PM can list the open work: the open work items in the recorded summary equal a direct ledger query, and the new PM's answer to "list the open work" in its transcript matches that list.
- (f) the PM pull path: with the operator typing in the PM pane nothing is ever typed into it (oracle: pane input history shows only the operator's keys); a message reaches the PM through `inbox` and `wait`, moves to `sent`, and reaches `acked` only by an explicit `cstan ack`; operator typing during a `wait`, an Esc interrupt of the `wait`, a `wait` that hits the shell-command timeout and a `wait` sent to the background each leave printed messages `sent` and later `unacked` if never acked, never `acked` and never lost (oracle: message log after each case); several queued worker reports are delivered one per ack in order with none dropped; the PM is not flagged by stall timers during a registered `wait`, including a backgrounded one (oracle: finding log); a PM that loops in `wait` without acking reaches `unacked` and triggers a notification, while the ack and notification timers do not run when the PM works outside a `wait` (oracle: message log, notification record and timer log); a PM message left unacknowledged past `pm_notify_after` raises a `herdr notification`, repeated at the configured interval, and the fallback pane plus bell works with the notification disabled; the per-loop context cost of `wait` is measured and recorded; optional item: with `--setting-sources project,local` the operator's hooks do not run in the PM, the Capstan hook does, and the PM's Herdr state still works.
- (g) a message that expires or goes unacked blocks the next message to that recipient until a recorded resolution (oracle: message log ordering).
- (h) a new worktree path either starts without the trust dialog (pre-trusted; oracle: a pane read before the first prompt shows no dialog, and the recorded host configuration entry for that path exists) or the dialog is handled by the logged exception in section 8 (oracle: the dialog log shows the path read, the option chosen and each keypress).

## 13. Verification approach and cost

Deterministic tests for the message state machine, framing, fact verification and the migration. Real-host scenarios with Claude Code in an isolated named Herdr session (the spike's pattern), with evidence and negative results kept; no canned agent replies as evidence. Real-host runs spend the operator's Claude account, so each stage states its expected usage and the operator sets a cap before any long run. No cap has been set yet.
